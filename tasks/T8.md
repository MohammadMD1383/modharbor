## B19. `doctor --json` emits `{}` for every finding

`finding` (`internal/cli/doctor.go:28`) has four unexported fields, so
`encoding/json` writes empty objects. Reproduced on a broken jar:

```json
{ "instance": "d", "errors": 0, "warnings": 2, "findings": [ {}, {} ] }
```

Severity, title, detail and fix never reach the wire. `doctor --json` is
unusable for automation; the counts are the entire machine-readable output.

- Add JSON tags to `finding` exporting severity, title, detail and fix.
- Confirm `doctorReport.Findings` is already tagged `[]finding` and leave the
  report's own shape alone unless a field is missing.

## B20. `doctor --json` always exits 0

`internal/cli/doctor.go:115-122` returns `printJSON(rep)` before reaching
`exitWithCode(1, nil)`, so error-severity findings do not affect the exit
status in `--json` mode while the human path exits 1. A script gets a
different verdict depending on a formatting flag — the worst kind of bug in a
CLI.

- Make the exit status depend on `rep.Errors` in both paths.
- The JSON must still print in full before exiting non-zero; nothing may be
  truncated or interleaved.
- Check whether any other command has the same early-return-before-exit shape
  and fix it if so — say so in your report either way.

## B21. `projectKey` mis-parses a URL with both a trailing slash and a query

`internal/cli/add.go:395-398` trims the trailing slash before stripping the
query string, so `https://modrinth.com/mod/lithium/?tab=versions` yields
`"lithium/"` — not a valid key, so it 404s. Slash-before-query works;
together they do not.

- Strip the query string first, then the trailing slash.
- Cover: bare slug, all four URL forms, trailing slash, query string, both
  together, and leading/trailing whitespace.

## B22. The better "no instance" error is unreachable dead code

`requireInstanceArg` and `missingInstanceError` (`internal/cli/helpers.go:52-67`)
are written, documented, and tested — but no command calls them. Only
`root.go:56` type-asserts for the error. So `Execute`'s
`try: modharbor instances` hint can never fire, and users get
`ResolveInstance`'s thinner message instead.

- Decide: wire it in, or delete it. Wiring it in is better — the message
  already exists and reads well, and T3's `helpers_test.go` already tests it
  (read that test before deciding; if you delete the function you must also
  remove or rewrite that test, which is a real signal the function is wanted).
- Every command that resolves an instance should go through the same path, so
  the message is identical everywhere. Use `pickInstanceArg`/`requireInstanceArg`
  consistently rather than adding a third idiom.
- Do not change which instance a command resolves. Only the error surface is
  in scope.
