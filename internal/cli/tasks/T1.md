# Task T1 — P0 correctness fixes (B2, B3, B4, B5, B6)

## Context

A documentation pass reviewed the CLI against its own `--help` and the
README, and found several defects where the documented behaviour and the
actual behaviour disagree. They are grouped here because they all live in
`internal/cli` and share the same fix surface.

Work in a git worktree branched from `main`:

```
git worktree add ../modharbor-t1 -b fix/p0-cli-correctness main
```

## Rules

- Only touch `internal/cli/**` and `README.md`.
- Do not change behaviour any other command depends on.
- Keep the existing UI helpers and style. `ui.Success`, `ui.Warn`, `ui.Info`,
  `ui.Note` and `ui.Failure` both print and return a string; call them as
  statements and use `ui.OK`, `ui.Bad`, `ui.InfoC`, `ui.Warnc`, `ui.Muted`
  for inline fragments.
- Every fix needs a regression test. `internal/cli` has none today, so you are
  creating the harness; keep it stdlib-only (no new dependencies).

## B2. `add --dry-run` downloads anyway

`internal/cli/add.go` declares `--dry-run` and never uses it. The flag reaches
only the trailing `ui.Hint`, so the jar is downloaded and installed, then the
command claims nothing was written.

- Thread the flag into `installProjects` (`internal/cli/install.go`).
- When set: resolve every project and dependency, report what *would* happen,
  and perform no network write and no filesystem write. Resolution itself
  needs the API, so API calls are fine; only the download and the write to
  `mods/` must be skipped.
- Report the count as "would install" rather than "installed", so the summary
  is not a lie in either mode.
- Test: build a temp instance with a jar, point the fake Modrinth at it, run
  with `--dry-run`, assert the plan is reported and `mods/` is byte-identical
  afterwards.

## B3. `add` and `remove` ignore `-i/--instance`

`splitArgs()` (`internal/cli/add.go`) returns an empty instance reference when
the last argument does not look like an instance, and nothing then falls back
to `flagInstance`. `-i` is silently dropped.

- `splitArgs` must fall back to `flagInstance` and then the config default.
- Be careful not to break the positional form `add sodium 26.3-fabric-mod`.
- Test both: `add -i <inst> sodium` and `add sodium <inst>` resolve the same
  instance.

## B4. `update --all` reports the empty run

`internal/cli/update.go` calls `eng.Run` to plan and then again to apply.
Because the first call already wrote the changes, the second finds nothing and
prints "nothing changed" after a successful update.

- Plan with `Options{DryRun: true}`, then apply the selected mods in a single
  non-dry pass.
- Make sure the interactive multi-select path still re-plans correctly with
  the narrowed `--include` set, and that `--all` / `--yes` skip it.
- The summary must reflect the pass that actually wrote.
- Test: one fake project with a newer version; run with `--all`; assert the
  new jar exists and the output reports it installed.

## B5. `list --all` documented but nonexistent

The README example block shows `modharbor list --all`; the real flag is
`--known`. Fix the README. Do not add an `--all` alias: `list` shows every jar
by default and `--known` is the useful filter.

## B6. `search` prints one letter per row

`internal/cli/search.go` renders `h.Slug[:min(1, len(h.Slug))]` as the first
column. Drop the column entirely; the project title is the useful identifier
and `slug` already appears in `modharbor info` output.
