## B23. `SortableGameVersions []string` cannot decode real payloads

`curseforge.go:56` (`GameFile`) and `:71` (`ModFile`) declare it `[]string`.
CurseForge sends game version **ids**, which are numbers. One such file
anywhere in a listing fails the entire decode:

```
json: cannot unmarshal number into ModFile.sortableGameVersions.0
```

so the whole project reports "publishes nothing" and every sibling file in
the response is lost. Note the existing inconsistency: `GameFile.GameVersions`
is `[]int` while `ModFile.GameVersions` is `[]string` — the package already
disagrees with itself about the same API.

- Accept **both** shapes rather than guessing which one the API sends: write a
  small tolerant type (custom `UnmarshalJSON`) that takes a number or a
  string and yields a string. Real APIs change and this must not 500 on a
  mixed payload.
- Decide deliberately what `Supports` should compare against (see B24) and
  make the two fields' roles explicit in comments.
- Do not "fix" this by changing `GameVersions []int` to strings — the numeric
  ids are meaningful and dropping them loses information.

## B24. `hydrateFingerprints` copies numeric ids into `GameVersions`

`curseforge.go:393`:

```go
if len(f.GameVersions) == 0 && len(f.SortableGameVersions) > 0 {
    f.GameVersions = f.SortableGameVersions
}
```

If those are ids, `Supports` compares `"432"` against `"26.3"` and rejects
every file for every Minecraft version. The comment calls this "the more
reliable MC version list", which is the assumption that has to change.

- Ids must be resolved to version names, or not copied. The client already has
  a `GameVersionID`/lookup helper — check whether a cache or lookup can supply
  names, and if resolving costs a request per id, say so and take the cheaper
  option rather than silently making a network call per file.
- Whichever you choose, `Supports("26.3", …)` must be true for a file that
  genuinely supports 26.3, and false for one that does not.

## B25. `Supports` silently ignores its `loader` argument

`curseforge.go:412-415` is `_ = loader`. CurseForge records loaders on the
**project**, not the file. So a Forge-only file passes a Fabric check, and the
loader veto in `internal/resolver` — the mechanism that stops modharbor
installing the wrong loader — silently stops applying.

- Resolve the loader from the project's categories, or drop the parameter so
  callers cannot believe they are being filtered. Read `internal/resolver`'s
  use of the provider before deciding; if the veto must keep working, the
  provider has to supply the data.
- A caller passing an unsupported loader and getting `true` back is the bug.
  Never return `true` for a loader you did not check.

## B26. A `null` response body decodes to a zero value with no error

Every endpoint. T7 pinned `null` as "the one silent zero value" — a phantom
empty project with no error, which then reads as "this mod publishes nothing".

- `do` should reject a `null` body explicitly.
- Distinguish "API returned null" from "mod genuinely has no files"; they are
  different failures and the message should say which.
